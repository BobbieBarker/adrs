# ADR-001: Compile-time dependencies

## Context

Macros run at compile time, so using any macro adds a compile-time dependency from the calling module to the module that defines the macro. That dependency is expected and usually cheap.

The anti-pattern appears when the *arguments* passed to a macro also become compile-time dependencies. A macro that receives a module reference and embeds it into the module body (a module attribute, an `@before_compile` accumulator, anything outside a function clause) records that referenced module as a compile-time dependency of the caller, even when the referenced module is only invoked at runtime.

A compile-time dependency forces dependent recompilation: changing the referenced module, or any module in its transitive runtime dependency graph, forces the calling module to recompile. In a builder-style API (a request pipeline, a router, a plug stack) where many modules are registered through one macro, a single edit can fan out into a large recompilation graph and dominate incremental build time.

## Decision

### Rule 1: Expand module literals into the function context where they run

When a macro stores a module reference for use inside a generated function, expand the literal as if it already lived in that function with `Macro.expand_literals/2`, so the reference is recorded as a runtime dependency.

**Correct:**

```elixir
defmodule MyApp.Pipeline do
  defmacro __using__(_opts) do
    quote do
      Module.register_attribute(__MODULE__, :stages, accumulate: true)
      @before_compile MyApp.Pipeline
    end
  end

  defmacro stage(mod) do
    mod = Macro.expand_literals(mod, %{__CALLER__ | function: {:call, 2}})

    quote do
      @stages unquote(mod)
    end
  end
end
```

**Wrong:**

```elixir
defmodule MyApp.Pipeline do
  defmacro __using__(_opts) do
    quote do
      Module.register_attribute(__MODULE__, :stages, accumulate: true)
      @before_compile MyApp.Pipeline
    end
  end

  defmacro stage(mod) do
    quote do
      @stages unquote(mod)
    end
  end
end
```

A caller registers stages, and `@before_compile` reads `@stages` to emit a `call/2`:

```elixir
defmodule MyApp.Web do
  use MyApp.Pipeline

  stage MyApp.Authentication
end

# generated by @before_compile:
def call(conn, _opts) do
  MyApp.Authentication.call(conn)
end
```

**Why:** In the wrong version, `stage MyApp.Authentication` runs at compile time and accumulates the module into the `@stages` attribute, outside any function body. That makes `MyApp.Authentication` a compile-time dependency of `MyApp.Web`, even though it is only ever called at runtime inside the generated `call/2`. Any change to `MyApp.Authentication`, or to its transitive runtime dependencies, then forces `MyApp.Web` to recompile. `Macro.expand_literals/2` resolves the literal as if it sat inside `call/2`, so the reference is tracked as a runtime dependency and edits to `MyApp.Authentication` no longer ripple back through the using modules. This holds only when the macro never calls a function on the module, accesses its structs, or reads its metadata at compile time. If it does any of those, the compile-time dependency is real and cannot be removed. To see which dependencies a file actually has, and whether each is compile-time, runtime, or export, run `mix xref trace path/to/file.ex`.

## Consequences

- Module references passed to macros are recorded as runtime dependencies instead of compile-time ones.
- Editing a referenced module no longer forces every using module, and its transitive graph, to recompile.
- Incremental compile times stay bounded as the number of registered modules grows.
- The technique applies only when the macro does not invoke functions, read structs, or inspect metadata of the module at compile time; when it must, the compile-time dependency is unavoidable.
